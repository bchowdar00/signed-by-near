## The stop at the deadline

**The gap.** The sampler (`collector/sampler.py`) checks `DEADLINE_UTC`, 2026-11-13T00:00:00Z, only between calls, and the client (`collector/nb.py`) waits for its call quota without checking it. On Nov 12 NearBlocks refused the run's call at 22:06:30Z. The run's ledger then held 300 credits in the last 24 hours, none leaving the window before 10:02:38Z Nov 13, so the sampler slept until then and would have called after the deadline. Its wrapper, `run.sh`, could not exit by itself either: its `wait` also waited for its own `caffeinate`, which waited for `run.sh`.

**The ruling, before the deadline.** Stop the sampler from outside at the deadline with a timer (`deadline/deadline_stop.py`, sha256 `79113bf9be2ea8471a52495b1c4dfc94f9fc5ee34f3e930e90f43c89248a62c5`). At 00:00:30Z it goes on only if the ledger's last line is dated before 00:00:00Z and is at least 60 s old (the client writes that line before it sends and times out at 40 s, so no request can still be in flight). It then marks the run stopped, ends the sampler, and releases `run.sh`. If a check fails it logs FAIL and touches nothing. Its offline test (`deadline/test_deadline_stop.py`, sha256 `529857fe7b2bdcdcf9219b8eb4836f235502780c29c87c88b3d51c0acf287a01`) runs the real `run.sh` with fake collectors: 4 cases, 14 checks, all passing on Nov 12.

**Outcome** (the timer's log, re-checked against the ledger, the stop markers and the process list):
- At 00:00:30Z the ledger's last line was the 22:06:30.531Z call, 6,839.5 s old: both checks passed, and the log has no FAIL line.
- 00:00:30.086Z: the sampler was sent SIGTERM; it had exited by 00:00:30.596Z, so no SIGKILL was needed. 00:01:34.217Z: `run.sh` exited.
- The ledger's last line did not change: no call was made after the deadline. It holds 944 lines.
- Every tier-1 family completed: census 48/48, flow 192/192, `sign` (last 12 months) 108/108. Three tier-2 families did not: migration 57/75, older `sign` 74/90, signature index 11/13. So 36 windows are not completed at the deadline.

**What it means for the reading.** The sampler was ended while asleep, so it did not write `not_completed` lines for the windows it had not finished; nothing was added by hand. The results' completeness table lists them as "pending", which here means "not completed at the deadline". Every measure gates on the same test of a window, so "pending" and "not completed" give the same reading.

## Readings that rest on an unfinished stratum

As stamped (`deadline/POST-FREEZE.md`, lines 56–64; that copy is available on request, and its sha256 is above):

> **Readings that rest on an unfinished stratum.** The frozen code still writes a number for a stratum whose windows did not all complete. An unfinished window keeps its frozen weight with empty values (`analysis/core.py:168`, `:607-608`), so totals and rates come from the finished windows only and run low. The frozen outputs then show those numbers:
> - `results.json` carries them with `complete: false`;
> - `tables.md` prints them beside "(not completed)";
> - THESIS prints the M10 early intervals beside a "not completed" verdict;
> - the charts draw them with no flag, because `analysis/charts.py` never reads `complete`.
>
> METHOD §6.10 says such a measure is "never estimated from the part done". The method governs. Everything the thesis shows a reader follows one rule: THESIS.md, its tables and both charts. A reading that rests on any unfinished stratum shows "not completed" and no number, interval, bar or dot.
>
> The rule depends only on which windows have a completed line. It was fixed and timestamped before any counted row was read. The frozen `results.json` and `tables.md` are published unchanged, with this note beside them. A script outside the frozen manifest applies the rule to make the published charts and the values THESIS.md prints. It changes no number it lets through.

What it covers (stamped, lines 66–74): every M3, M4 and M5 month with `complete: false`; for migration (M10), every series with any unfinished early or late stratum, whose early, late and difference readings and verdict all read "not completed" (the 22:15Z ruling: §6.10's backstop and §7 item 1 make the measure the unit, not the reading); chart 1's early and late marks for those series; chart 2's bars for an unfinished month, drawn as a marked gap; and every unfinished monthly migration point or signature-index month, marked rather than silently dropped. The destination-audit picks come from completed months only, and the months not completed are named.

**How it is applied.** `publish/rule.py` runs the frozen command (`analysis/recompute.py`) unchanged, whose `out/` is published as it is, and then writes `out/published/`: the same results with every reading on an unfinished stratum masked (its values null, marked `"not_completed": true`, with the reason listed under `rule`), the frozen `tables()` and charts drawn from them, and a visible "not completed" mark and footnote wherever a chart would have drawn a masked value. Points on how it reads the rule:
- "A completed line" is read through the gate every frozen measure uses, `core.Study.window_complete`: a `completed` line, plus the window's transaction resolution read and its pages a gapless chain (DEVIATIONS items 12 and 17). A window that fails the gate is one the frozen code itself leaves empty, so this reading can mask more than the plain words, never less. The script lists any window that has a completed line but fails the gate. Such a window raises the count of windows not completed above the 36 counted by completed lines; THESIS prints the gate's count, and `AFTER-READ.md` names any such window. It never reads a value from a window to decide.
- A reading the frozen code itself labels "not completed" for another reason (for example the trend without class 2a, if a month's neardata sample were missing) is masked the same way, by the same method rule.
- What a reading rests on, where the frozen results do not list its strata: M9 and the flow checks on every flow stratum; a chain's route reading (M1) on its own flow strata, and whether Omni is seen in use on it also on the census; the counts over the 28 chains on every chain's reading, and the "Omni dominant on five chains" test on the route readings; the census's per-token counts on the census. M6's key-type shares come from the neardata block sample alone and stay; its rates per day use the month's `sign` calls and are masked with the month.
- As for migration (the 22:15Z ruling), the unit is the measure: a reading is masked whole when any stratum it rests on is unfinished, even where the frozen value would come out the same whatever that stratum held. So with a census window short, every chain's "seen in use" is masked, including chains where the flows alone show Omni in use. This can only blank more than strictly needed, never show a number that rests on an unfinished window; by their completed lines, tonight's 36 windows include no census or flow window.

The frozen code already counts a chain with an unfinished flow stratum as undecided (`analysis/measures.py:159-171`, `:843-851`). - Kept inside a masked reading: what describes it rather than measures it (its month, strata, token names, the frozen code's own state or verdict words, calendar days), and figures that rest on no window (the HSP-007 ledger amounts, NearStats' reference volume, the 28-chain documentation, how many chains the design can read).
